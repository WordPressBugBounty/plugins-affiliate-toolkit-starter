== Installation ==

1. Upload the plugin via **Plugins → Add New → Upload Plugin** or extract the zip file into the `wp-content/plugins/` directory.
2. Activate the plugin from the **Plugins** page.
3. Navigate to **affiliate-toolkit → Shops** and create a new shop (e.g. Amazon with Creator API).
4. Import products via **affiliate-toolkit → Products → Import** or create them manually.
5. Display products in your posts or pages using the **Gutenberg product box block** or the **shortcode generator**.

== Frequently Asked Questions ==

**Is the plugin completely free?**
Yes, the core plugin is completely free and includes product management, templates, and Amazon integration.

**What if I need more features?**
Premium extensions for additional networks (AWIN, eBay, CJ, etc.), AI content generation, price history, and more are available at [affiliate-toolkit.com](https://www.affiliate-toolkit.com/).

**Do I need an Amazon API key?**
No. You can use the Amazon Creator API or the No-API mode to import products without the traditional Product Advertising API. However, using the PA-API gives you access to more product data and automatic updates.

**Which affiliate networks are supported?**
The free version supports Amazon. With premium extensions you can connect to AWIN, eBay, Commission Junction, Tradedoubler, and 20+ other networks, or import products via CSV feeds.

**Does the plugin work with my theme?**
Yes, affiliate-toolkit is designed to work with any WordPress theme. All templates are fully responsive and adapt to your theme's styling.

**Is the plugin compatible with caching plugins?**
Yes, it works with all major caching plugins including WP Rocket, W3 Total Cache, WP Super Cache, and LiteSpeed Cache.

**Can I use the plugin with Gutenberg?**
Yes, affiliate-toolkit provides a dedicated Gutenberg block for displaying product boxes directly in the block editor. You can also use shortcodes in any editor.

**How do I display products on my site?**
After importing products, you can display them using the Gutenberg product box block or the shortcode generator. The shortcode generator lets you choose from different templates and search for products directly.

== Changelog ==
= 3.9.5 =
*   NEW: Shops, Products and Lists are the first entries of the affiliate-toolkit menu again. "Importsets" and "Redirects" (extensions Importset and Influencer) were listed above them and the menu opened the importsets; they now follow the product import.
*   NEW: The sub shops in the shop selection (product, list, bulk import, shortcode generator, shop replacement) are indented below their main shop.
*   NEW: The sub shops in the shop selection (product, list, shortcode generator, filters) are sorted alphabetically within their main shop. The main shops were already sorted by title, their sub shops appeared newest first.
*   SECURITY: The license requests to affiliate-toolkit.com (activate, deactivate and check license) now verify the TLS certificate (sslverify was false). Anyone able to answer these requests in place of the store could otherwise report any license status to the site.

= 3.9.4 =
*   FIX: The cronjob could loop endlessly on a single queue entry. The entry is taken out of "prepared" by writing its result back, but WordPress refuses a write completely when a value does not fit its column - and the error message of a failed CSV download contains the whole feed url, which exceeded the 700 characters of the message column. The status was never stored, the same entry was fetched again, and the feed was downloaded over and over: via cronjob url until the server aborted the request, via WP-CLI without end. The message column now holds a long text, values are shortened to the actual column length before they are written, a rejected write is retried with a reduced message, and the queue processing additionally stops a batch that comes back unprocessed twice and marks it as an error.
*   FIX: A product whose data did not fit the columns of the internal tables was dropped completely and without a message, because WordPress refuses the whole write instead of shortening a single value. Affected were long product titles, long tracking urls and in particular the variation name, which is stored serialized but had only 250 characters available. The existing second attempt only removed unusual characters, not the length, so the product was simply missing from the list or kept its previous data. Values are now shortened to the actual length of their column before they are written; the serialized columns are left empty instead of being shortened, because a shortened serialized value can no longer be read back. The variation name now holds a long text.
*   FIX: Any change to the structure of the list table would have failed, because its two indexes were created with an unconditional ALTER TABLE and a second run ends with "Duplicate key name". They are now only created when they are missing, as in the product table.
*   SECURITY: Removed the file-writing branch from the discount-notice handler. ATKP_StoreController::get_product_discounts() fetches the current promotion from affiliate-toolkit.com (wp-json/affiliate-toolkit/v1/aktion) and, when the response carried an "aktion_filename" and "aktion_filecontent", wrote that content verbatim into the uploads directory with file_put_contents() - a response from the store could therefore place an arbitrary file, including executable PHP, into the installation. The store no longer sends those fields, and the handler now only decodes and caches the promotion text; the file write is gone. The notice continues to show the promotion as before.
*   SECURITY: The discount-notice and add-ons feed requests to affiliate-toolkit.com now verify the TLS certificate (sslverify was false). With the file write already removed this was no longer a code-execution risk, but there is no reason to skip certificate verification for these feeds, so it is on now.
*   FIX: The "Medium image" entry in the template editor's toolbar inserted get_mediumimage($product), but that formatter method did not exist (it was misspelled get_mediumnimage), so any template using it stopped with a fatal error. Both spellings now work, so existing templates keep working.
*   FIX: Product boxes and lists could show "Price:" with no value when the shop's currency was set to "Format from merchant". The formatter used the base price instead of the sale price as the merchant-formatted value, because get_saleprice_fallback() and get_baseprice_fallback() returned each other's value. Both now return the right value, and if the merchant sends no formatted price, the plain number is shown.
*   FIX: For products with variations, the shipping cost of the first variation was never read because of a typo in the field name. Shipping and total price are now correct for these products.
*   FIX: In the price comparison, offers with the same shop title, price and shipping were not merged when "group shops" is enabled, because the comma removal in the title was written the wrong way round. Duplicate offers are now merged as intended.
*   FIX: Fetching a product's image gallery without the main image (get_images($product, false)) caused PHP warnings, and missing image sizes were not filled in from the main image. The main image is now always used as the fallback.
*   FIX: The shop sort order ("Sort order" on the shop) was ignored in the price comparison unless one of the "Main product and ..." sort modes was selected, because of an operator precedence error. It now applies in every sort mode, and in "Main product and ..." modes the main product's shop stays first.
*   FIX: Functions like atkp_get_product() and the product box helpers could throw a TypeError when given a product or list id that does not exist. They now return an empty result instead.
*   FIX: The price trend text (get_minpricedays) was hard-coded in German, measured "constant for N days" from a fixed date in 2010, and could read past the end of the price history. It now compares against the shop's actual price history, shows the old and new price formatted in the shop's currency, and is translatable English with German translations included.
*   FIX: The "Import product" search in the shortcode generator always failed with an error, because the server checked a security token (nonce) under a different name than the one the generator sends. The same search in the Gutenberg product and list blocks sent no token at all. Searching a shop and importing a product from the generator and from the blocks works again.
*   FIX: The live preview in the template editor always showed "invalid nounce" instead of the rendered template, because the preview request did not send its security token. The preview renders again.
*   FIX: The template editor showed plain text fields without syntax highlighting and threw a JavaScript error, because it looked for a CodeMirror version that WordPress no longer loads. It now uses the editor bundled with WordPress. If syntax highlighting is turned off in your user profile, the plain text fields keep working, including inserting placeholders from the template bar.
*   FIX: The "Custom fields" and "ACF fields" menus of the template bar showed raw HTML code instead of clickable entries, because the links were escaped a second time. The entries can be inserted into the template again.
*   FIX: On a fresh installation, link tracking, the image gallery and the slider did not work until the settings had been saved once. Until then the plugin's inline script was attached to a script that WordPress never loaded, so it was silently dropped. The script is now always output.
*   FIX: The external cron URL returned HTTP 200 for a wrong key or a deactivated external cronjob, so monitoring tools did not notice the problem. It now returns 401 and 404. The cron error page also no longer shows server file paths, error messages and stack traces to anyone who opens the URL. These details now only appear on the command line or with WP_DEBUG, and are always written to the PHP error log.
*   FIX: The cronjob status on the settings page always told WordPress-cron users to check a server-side cronjob, because the cron type was compared with a number instead of "wpcron". WordPress-cron users now get the matching hint to save the settings page and re-register the scheduler.
*   FIX: Importing a product by EAN through a shortcode (e.g. [atkp_product ean="..."]) did not find an existing product with that EAN and could create a duplicate, because the EAN was never passed to the duplicate check. A product or list imported automatically by [atkp_product asin/ean="..."] or [atkp_list keyword="..."] was also not displayed on the first page view, because the new post id was read from the wrong place.
*   FIX: The bit.ly link shortener could not work. When shop links were refreshed, the API key was passed in place of the url, and empty links caused a PHP TypeError. Links are now shortened with the correct values, and empty links are skipped.
*   FIX: The shortcode generator and the Gutenberg product block showed German texts (e.g. "Importieren", "Fehler bei der Suche", "Produkt bearbeiten", "Ausgabe wird im Frontend gerendert") in English backends. All of these texts are now English and translatable, with German translations included.
*   FIX: The help and warning texts on the settings pages were always shown in English, because display_helptext() and display_warntext() never passed them through the translation. They are now translated.
*   FIX: The "not found" messages for shops and templates said "No lists found", and the debug page labelled the button that recreates the product table "Drop & create list table". Both texts are corrected.
*   FIX: The default price colour of templates was the invalid value "#00000" (five digits), so browsers ignored it. It is now "#000000". The default button size "mormal" was corrected to "normal" (the output is unchanged).

= 3.9.3 =
*   SECURITY: Fixed a stored Cross-Site Scripting (XSS) that low-privileged users (Contributor and above) could use to run JavaScript in an administrator's browser, reported by the Wordfence Threat Intelligence team. The product link fields were stored and printed without any escaping: the "url" cast in ATKPTools::get_casted_value() returned the submitted value verbatim (the sanitization had been commented out), and on output atkp_formatter::build_external_link() concatenated the url straight into the href attribute through a urlencode() helper that did nothing - no esc_url(), no esc_attr(). A product url containing a double quote therefore closed the href and injected arbitrary markup, for example x"><img src=x onerror=...>, which executed for anyone who viewed the product. Because the atkp_product post type is editable with edit_posts (capability_type "post") and the save handler only verified its nonce, a Contributor could store such a url on a draft product, embed it anywhere with [atkp_product id=..], and the payload ran when an administrator previewed the pending post - a draft product renders on purpose. The same raw-url pattern affected the add-to-cart, customer-review and manual-offer link fields and the product image urls, which were emitted into <img src=".."> without escaping as well. The urls are now escaped on output in every context: esc_url() for the href and for the six product image sinks, and esc_js(esc_url_raw()) for the JavaScript-link onclick variant - esc_url() alone is not enough there because its display encoding of a single quote is decoded again inside the onclick handler and would reopen the break-out. As defence in depth the "url" cast now returns esc_url_raw() so a double quote can no longer reach the stored meta value, and product_detail_save() now checks current_user_can( 'edit_post', $post_id ) in addition to the nonce, so the save handler enforces per-post authorization instead of accepting any product id backed by a valid nonce.
*   SECURITY: Fixed an arbitrary file upload leading to Remote Code Execution by low-privileged users (Contributor and above), reported by the Wordfence Threat Intelligence team. The product image import took the file extension of the downloaded image from the url path and only replaced it when the server's Content-Type mapped to a known WordPress image mime type. An attacker who controls the image host could answer with a Content-Type that starts with "image/" but is not a registered mime type (for example image/x-custom): the download check passed, get_extension_for_mime() returned nothing, and the extension taken from the url - "php" for http://attacker/shell.php - was kept. sanitize_file_name() does not strip a .php extension, so file_put_contents() wrote the attacker's PHP body to wp-content/uploads, where a default server executes it. The product save handler only verified its nonce, and the atkp_product post type is editable with edit_posts, so a Contributor could read the nonce from the editor and save a draft with a prepared image url; the only non-default precondition was the administrator-set "import product image" option. The saved extension is now validated against the image extensions WordPress knows (wp_get_mime_types() filtered to image/*): when the extension derived from the url and content type is not an image extension the real type is detected from the downloaded bytes with getimagesizefromstring(), and a download that is not a genuine image is refused instead of written. In addition download_image() no longer trusts a content type merely because it begins with "image/" - a response is only accepted when its content type is a registered image mime or its bytes are a real image, so a non-image body served as image/x-custom is rejected at download time as well.
*   SECURITY: Hardened the path that resolves a template name to a file (defence in depth, no exploit known). A template reference that is not a post id is resolved as a relative path below the template directories ("<view>/<name>.blade.php"), and the reference reaches that code from a shortcode as well as from the AJAX render endpoint, where it is taken straight from the request - for any logged-in user, and without a login whenever AJAX loading or the AJAX handler is enabled. A name containing a parent reference therefore left the template directories, and whatever the path resolved to would have been compiled and executed by BladeOne. A template name is now checked before it is used in a path (letters, digits, underscore, dash and the dot of the Blade dot notation, no directory separators, no parent references) on all four paths: the product output, the live search output, the search form output and the @include/@extends resolution inside the template engine.
*   SECURITY: The "Templates" admin page was registered in the menu with the edit_pages capability, although the page itself has required manage_options since 3.9.1 - an editor saw the entry and ran into the error page. The menu entry now carries the same capability as the page.
*   SECURITY: The compatibility mode for old templates read the template fields of the given id without checking that the id really belongs to a template post, which is the pattern that was fixed for the Blade render paths in 3.9.1. The old templates are filled in by placeholder replacement and are not compiled, so this was not exploitable for code execution, but the id now goes through the same guard as everywhere else (requires the "Template Compatiblity Mode" extension 1.0.5).
*   FIX: The "searchtemplate not found" error of the search form printed the requested template name unescaped (requires the "Frontend Search & Filter" extension 1.0.11, and only applies when "hide error messages" is off).
